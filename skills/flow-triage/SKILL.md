# flow-triage: promote a captured item into a buildable ticket

The middle step of `/flow-park` -> `/flow-triage` -> `/flow-ship-issue`. A capture
records an observation. A ticket records a decision. This skill does that
conversion, and it is a **promote**: the file that arrives is rewritten, and
moved to where its new shape belongs. One file arrives and one file leaves.
Nothing is copied, and no file is left at the old path.

Forked from `triage` in `mattpocock/skills`.

## Nothing installed, nothing written

If `~/.flow-factory/tracker-contract.md`, `~/.flow-factory/templates/ticket.md`
and `~/.flow-factory/settings-contract.md` are not all readable, the factory was
never installed on this machine. Say so and stop. Do not rebuild a shape from
what this file describes: a ticket missing a section is worse than no ticket,
because every skill after this one reads it as complete.

Check first that this project has a `flow-factory.toml` at its root. If it does
not, stop as `~/.flow-factory/settings-contract.md` says.

## The shape you write comes from two files

- `~/.flow-factory/templates/ticket.md` is the ticket body. Its sections, in its
  order, and the authoring guidance inside each section is the instruction for
  what to put there.
- `~/.flow-factory/tracker-contract.md` owns the statuses, the headings, the
  three file shapes and how to tell them apart.

Read both. Do not restate either one here or in your own notes. Eight of the
contract's eleven statuses are yours to write, so a restatement that drifts is a
skill writing statuses no other skill matches.

Project settings are read per `~/.flow-factory/settings-contract.md`. That file
holds the rule for every key named below, including what an unset key means.
No key's rule is repeated here.

## States you own

`needs-triage` is the queue. From there an item leaves for `needs-info`,
`ready-for-agent`, `ready-for-human`, or `wontfix`.

`blocked` is a fully specified ticket waiting on a ticket named under
`## Depends on`. It is not the queue: nothing about it needs evaluating, and
the only question is whether its blockers have landed. Step 0 answers that and
promotes it, or puts `blocked` back.

`backlog` also arrives here, because `/flow-ship-issue` refuses to build one. It
means the user parked the work on purpose, so it is not a rejection and not a
queue item. Treat it as a question rather than a promote: ask whether it is time
to work this, and only then triage it.

`in-triage` means a session has claimed the file for triage. You set it yourself
at pickup, see Step 0, and every exit clears it. A file already reading
`in-triage`, `in-progress`, `in-review` or `done` when you arrive is another
session's: say so and stop. `in-progress`, `in-review` and `done` are otherwise
`/flow-ship-issue`'s and `/flow-close-out`'s. A status in neither of those groups
is undocumented: ask what it means rather than reading it as one of yours.

## The disclaimer

Every block you append under `## Comments` starts with:

```
> *This was generated by AI during triage.*
```

## Invocation

The user types `/flow-triage` and says what they want, or another skill invokes
this one with a file path. A bare path with no request is the second branch:
start at Step 0. Three branches:

- **"show me what needs attention"** -> the queue view below.
- **a named item or path** -> Step 0 onward.
- **"move it to ready-for-agent"** -> trust them, apply the status directly, skip
  the grilling. First say whether the file carries `## Acceptance`. Without it
  there is nothing to build against, so offer to write it before you flip. Say
  nothing about `## How to verify`: an empty one is legal, see Step 5.

## The queue view

Three buckets, oldest first:

1. **`needs-triage`** -> in the queue.
2. **`needs-info`** -> show each one's open question and who owes the answer, so
   the user can answer it here and now. A local tracker has no reporter-activity
   signal to wait for, so the queue view is the exit.
3. **`blocked`** -> show the blocker each one waits on and that blocker's
   current status, so the user sees what is stuck and on what.

Counts, then one line each. Let the user pick.

For the whole-project backlog across every status, that is `/flow-backlog`. This
view is the triage queue only.

## When a skill this one names is not installed

Several steps below hand off to `/flow-reground`, `/flow-grilling` and
`/flow-grill-with-docs`. Two ways a handoff can fail to answer, one rule:

- The skill runs and stops itself. `/flow-reground` stops on `FETCH_FAILED`.
- The skill is not installed on this machine at all.

In both cases triage overrides the stop and continues. Judging a file against a
check that did not run is fine; inventing its result is not. Do by hand whatever
the file alone lets you do, then name the check as not run, or as stale, in your
recommendation. Never report a verdict the check did not produce.

## Step 0: promote, or evaluate?

**Claim it first.** Flip `Status:` to `in-triage`, no ask. Write the `Session:`
line where "Header lines" in `~/.flow-factory/tracker-contract.md` puts it,
holding the value of `$CLAUDE_CODE_SESSION_ID` (run
`echo $CLAUDE_CODE_SESSION_ID` to get it). That is your first write, before the
re-ground and before any exploration.

`Session:` is transient: the line is removed whenever the status leaves the one
the skill claimed with, so a file at rest carries none. `/flow-ship-issue`
claims with `in-progress` and removes the line at the flip to `in-review`, for
the same reason. The `Status:` line is what stops `/flow-conductor` dispatching
the same file twice; the `Session:` line records which session holds the claim,
so a person inspecting a stuck `in-triage` file can tell an abandoned run from a
live one. `/flow-conductor` does not read it. Every exit below flips `Status:`
again and removes the `Session:` line, so the claim clears itself. The one
exception is the outstanding-blocker stop just below, which puts `blocked` back
and removes the `Session:` line.

Use the contract to tell what arrived. A file that arrived as `blocked` is
waiting on its blockers rather than on a judgment. So is a spec-cut ticket at
`needs-triage`, written before `blocked` existed: a file carrying
`## Acceptance` is already a ticket, and one that also carries a
`Slice <X.Y> of PRD.md` provenance line was cut from a spec by
`/flow-to-tickets`, whose quiz was the specification gate. Either way:

- Every named blocker is satisfied, by the rule under "When a dependency is
  satisfied" in `~/.flow-factory/tracker-contract.md` -> **promote it**, after a
  re-ground. Run `/flow-reground`, because a file that waited on blockers was
  specified against a codebase that has since changed, and its mechanism is stale
  by default. Then split what you found the way `/flow-ship-issue` Stage 0 does:
  - **Mechanical** staleness, where the named mechanism, paths, symbols, versions
    or commands no longer match the codebase. Patch it, and say in the triage
    notes what you replaced and what you verified it against.
  - **Substantive** staleness, where what the ticket delivers has moved: a
    criterion is now invalid, the work is already built, a criterion needs adding
    or removing. **Propose it, do not apply it**, and stop. That is a re-spec.

  Also fill any section of `~/.flow-factory/templates/ticket.md` the file is
  missing. Then flip `Status:` to `ready-for-agent`, append the promote entry
  under `## Comments` as Step 5 describes, and stop.
- A blocker is outstanding -> name which one, put `Status:` to `blocked`, and
  stop. `blocked`, not `needs-triage`: the file needs no evaluation, and putting
  it in the queue would send the next triage back through this same check.

Anything else is a real triage. Continue.

## Step 1: gather context

Read the whole file, `## Comments` included, so you do not re-ask a resolved
question. Three checks against the codebase:

- **Redundancy.** Search these angles, and name in the verdict which ones you
  ran, the terms you searched per angle, and their hits:
  - **Code symbols.** The domain term as the code spells it.
  - **Test names.** The same concept as a test would name it.
  - **The user-facing label**, only when `docs.glossaries` is set. Translate the
    domain term through the first file in that list, then search user-facing
    strings and routes for that other name. Unset, this angle does not run: with
    no glossary there is no second name for the concept, and searching the
    strings for the term you already searched is the first angle again. Do not
    invent a replacement angle, and never state a fixed number of angles.

  Already built is a `wontfix`.
- **Prior decision or duplicate.** Grep the concept across `.flow/issues` and
  `.flow/candidates`. A `wontfix` hit carries the argued rejection, so the
  decision already exists. An open hit is a duplicate: name the older file and
  propose merging into it.
- **Still true?** Run `/flow-reground`, and read its result with the same
  mechanical-or-substantive split as Step 0.

Read `docs.context` before you explore, when it is set. Check the terms you use
against every file in `docs.glossaries`. Treat the decision records in
`docs/adr/`, and anything listed in `project.decision_docs`, as already settled:
a triage does not re-open a decision either one already made.

## Step 2: verify the claim

Before any recommendation, check the claim holds. Reproduce the bug from what the
file describes, wherever it describes it: read for the claim rather than for a
heading. Report one of three: confirmed, with the code path; failed; or too thin
to test, which is a strong `needs-info` signal.

A confirmed claim makes a much stronger ticket, because the acceptance criteria
can then name a real observed value.

Then the assumptions ledger. List what the file takes for granted: the cause it
names, the mechanism it presumes exists, the feasibility of the change. Check
each against the code and mark it one of three: **verified**, with the evidence;
**unverified**; or **refuted**.

An unverified row the user lets stand goes into the ticket as an `Unverified:`
line, so the builder inherits the doubt instead of inheriting a guess:

- Under the acceptance criterion it threatens, indented with that criterion's
  reasoning.
- When it threatens no criterion, in `## Background`, with the facts the problem
  rests on. Not in `## Comments`: the builder reads the body first, and a doubt
  filed in the audit trail is a doubt the builder never meets.

## Step 3: recommend, then wait

Present a decision brief and wait for direction. You recommend a status; the user
picks it. Never flip a status on your own judgment at this step.

Write the brief for a reader with no memory of the file: plain language, no
project shorthand, short sentences, one fact per sentence. Call each concept by
one name and hold it through the whole brief. Separate the items with blank
lines.

- **Where:** the place and moment the user meets it: which screen, during what
  action. For a change with no user-facing surface, the component it belongs to:
  which stage or service, in plain words. File paths belong in Scope, not here.
- **What:** the behaviour change itself, one plain sentence. Not its location:
  "stop showing a false reason", not "fixes on the confirm page".
- **Why:** what it costs today, and who hits it.
- **Today -> after:** one line per change: today's behaviour, then the behaviour
  once built. State the claim verdict (confirmed, failed, or too thin) once, for
  the whole item.
- **Scope:** what gets built and what stays out.
- **Size:** rough effort, so the reader knows how much attention the decision
  deserves. "Ten lines in one component" and "a new pipeline stage" decide
  differently.
- **Assumptions:** one sub-bullet per ledger row, each with its mark. Verified
  rows are what the reader audits; unverified or refuted rows are what they rule
  on.
- **Status:** the recommended status, with the single strongest reason.
- **Decide:** the decisions the user must make, numbered, each with a
  recommendation and what the alternative buys. A fact that would flip the status
  is one of these.

## Step 4: grill, when the request needs shape

Run `/flow-grilling`, one round of questions at a time. For the writing half,
follow `~/.claude/skills/flow-grill-with-docs/SKILL.md`, which sharpens domain
terms and owns where a settled term is written. Read it, do not invoke it: it is
user-invoked only.

## Step 5: apply the outcome

### `ready-for-agent`

Rewrite the file into the ticket shape:

- **Every heading the ticket template does not have is folded in and deleted.**
  A capture arrives with `## What was observed` and `## Why it matters`. The
  observation and its concrete detail become `## Background`'s facts and its
  worked example; the stakes become `## Background`'s opening. Neither heading
  survives, because the ticket's section list is closed and the contract allows
  one spelling per heading.
- **A superseded suggestion is replaced, not left standing.** Anything the
  arriving file proposed as an approach becomes `## Scope` and `## Acceptance`,
  and the original text goes. This is the failure mode of a promote: the builder
  reads the body first and builds the superseded plan.
- `## Comments` goes last, holding one dated block: what promoted this file and
  when, what you verified, and which body sections you replaced. That block
  carries the provenance and is the audit trail for the rewrite. A capture has no
  provenance line to rewrite, and the template defines one only for a ticket cut
  from a spec, so this entry is where the promote is recorded.

**The test command.** For a ticket that changes code:

- When `source.backend_dir` is set, these rules apply to the part of the work
  under that directory. Unset, the project is one tree and they apply to the
  whole ticket.
- When `test.guide_path` is set, name that guide in `## Scope` and say the
  builder takes the test type and the folder from it. Unset, write no guide
  sentence and name no path.
- When `test.command` is set, put it in `## How to verify`, as the command that
  runs the tests. Unset, write no command. Instead name `test.command` as unset
  in `## How to verify`, so the builder reads a stated gap rather than a guess,
  and carry on with the rest of the promote. The unset rule stops this step, not
  the triage: the reason a guessed command is forbidden is that it reports a pass
  for a run that never happened, and a command named as missing cannot do that.

Never put the command in `## Acceptance`. The guide picks the lowest test type
that exposes the failure, which is a build-time call. A command pinned as an
acceptance criterion would fail a builder who correctly chose a lower type.

Then flip `Status:`.

Done when the file carries every heading of `~/.flow-factory/templates/ticket.md`,
in its order, with none extra and none missing, and these six hold, whether this
rewrite wrote them or a Step 0 promote filled the gaps:

- `## Background` has its worked example.
- `## Acceptance` includes its falsification criterion.
- `## How to verify` carries the exact commands and the output that means each
  one passed, **or is empty**. Empty is a legal ticket and means the acceptance
  criteria carry their own commands, so the builder checks those directly. Never
  write a sentence naming a route to take.
- `## Depends on` is filled or reads "None, can start immediately."
- `## Scope` names real paths and real symbols.
- The file sits at its `.flow/issues/<feature>/<NN>-<slug>.md` path, per
  `### Where a promoted ticket lands` below. A promoted ticket still in
  `.flow/candidates/` is not done.

### `ready-for-human`

The same shape, plus one line under `## Goal` naming what stops an agent: a
judgment call, external access, a design decision, manual testing.

### Where a promoted ticket lands

Both exits above produce a ticket, and the contract says a work item lives at
`<tracker>/issues/<feature>/<NN>-<slug>.md`. So a capture being promoted moves
out of `.flow/candidates/` and into a feature folder. Move it last, after the
rewrite and after the `Status:` flip, so what lands is already finished.

- **Ask which feature folder.** List the folders under `.flow/issues/` and ask
  the user to pick one or name a new one. A capture belongs to no feature, so
  this is the user's answer and never yours. Do not read a folder off the
  capture's subject, and do not invent a catch-all such as `misc`.
- **Take the next free number.** Read the highest `NN` already in that folder
  and add one, keeping two digits. Numbering has gaps, so the file count is not
  the answer. A folder you are creating starts at `01`.
- **Keep the arriving slug.** The filename is that number plus the slug the
  capture already had. Renaming it breaks a link anyone already wrote down.

Nothing may be left at the `candidates/` path.

Only a promote moves a file. A file that arrived already under `.flow/issues/`,
such as a spec-cut ticket waiting on its blockers, stays where it is, and so
does a capture leaving for `needs-info` or `wontfix`. Only their `Status:`
changes.

### `needs-info`

Append the notes block below. Name one question and name who owes the answer. A
question with no owner never comes back.

```markdown
### Triage notes, <YYYY-MM-DD>

> *This was generated by AI during triage.*

**Established so far:**

- <point>

**Open question:** <one question, specific and answerable>
**Owed by:** <the user, or a named stakeholder>
```

Everything grilling resolved goes under "Established so far", so the work is not
lost while the answer is outstanding.

### `wontfix`

Close by editing the file. Flip `Status:`, and put the argued reason under
`## Comments` with a date and what closed it. The file is the rejection record,
and Step 1's prior-decision check reads it.

## Closing the turn

`✅ Triage done.` plus at most three lines. One plain sentence per line, about 15
words, no sub-points and no code identifiers. A line needing a second sentence
belongs in the file, not here. The user should read all three in ten seconds.

A line earns its place only if it changes the user's picture of the item: the
capture was wrong about something, or triage found something that changes what
gets built. Everything else stays in the file and is not repeated here, the
decisions the user just made and the notes for the builder included.

Then one final line: the file's path, and its new status. Plain, no verb and no
invitation, so it stays a location rather than a suggestion. It does not count
against the three lines. It is there so a user who wants to ship, dispatch or
reopen the item does not have to go and find the file.

`<the path of the file you just wrote>` -> `<its new status>`

Then stop. No "next", no dispatch suggestion, no offer of follow-on work.
Triage ends here; the user picks the next move.

## Resuming

Read `## Comments` first. Check whether the owed answer arrived. Present the
updated picture before you continue.
